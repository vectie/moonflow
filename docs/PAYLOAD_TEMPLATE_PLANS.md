# Materialize request templates into batch plans

Create one real JSON request per record, without hand-authoring a file for every
job. Start with a declared source operation, a request template for that operation,
and an explicit JSON-pointer mapping. Preview the exact generated bytes and
editable plan, then save the inputs and ordinary v2 draft together.

```sh
moonflow plan preview-payloads WORKSPACE source-graph.json mapping.json request-template.json records.json study 2026-07-31T00:00:00Z
moonflow plan from-payloads WORKSPACE source-graph.json mapping.json request-template.json records.json study 2026-07-31T00:00:00Z
moonflow plan inspect WORKSPACE study
moonflow plan prepare WORKSPACE study catalog.json 2026-07-31T00:00:00Z
```

Use actual evaluation time and current catalog health for real work. The complete
[synthetic furniture sample](../examples/payload-plan/README.md) uses July-dated
health fixtures and creates no adapter effects. Check the CLI exit status before
parsing output: existing error diagnostics are printed to stdout.

## Explicit mappings and typed values

```json
{
  "contract_id": "moonflow.payload-plan-mapping.v1",
  "records_pointer": "/jobs",
  "template_work_item_id": "make-model",
  "work_item_id_pointer": "/id",
  "depends_on_pointer": "/after",
  "bindings": [
    {"target_pointer": "/request_id", "value_pointer": "/request_id"},
    {"target_pointer": "/idempotency_key", "value_pointer": "/request_id"},
    {"target_pointer": "/operation/params/name", "value_pointer": "/name"}
  ]
}
```

`records_pointer` selects the record array from the export. All value selectors
and `work_item_id_pointer` address each individual record. `target_pointer`
addresses an existing location in the request template, which must be an object.
Each binding replaces that entire value: string, number, boolean, null, array or
object. Unselected template values are retained exactly as JSON values. Strings
are never evaluated, interpolated, trimmed or coerced; escaping and Unicode are
preserved in the parsed result. Object key ordering and whitespace are normalized
when writing generated bytes. This is not a raw template-file byte copy.

Pointers follow the existing records importer: empty selects the root; `/` selects
an empty object key; `~0` and `~1` escape tilde and slash. Array indices must be
canonical, in-range nonnegative integers. Targets cannot replace the root,
create missing paths, append arrays, overlap, or repeat. Sibling targets such as
`/a` and `/ab` are distinct. Every configured selector must resolve in every row.
A null selected value is an actual JSON null, not a missing-value fallback.

Optional selectors:

- `depends_on_pointer`: an array of new batch item IDs, supporting forward links
- `acceptance_criteria_pointer`: nonempty string array; default source criteria
- `timeout_ms_pointer`: integer 1..86,400,000; default source timeout
- `additional_input_artifacts_pointer`: an array of existing workspace-relative
  file references, appended after the generated primary request

Omitted or null optional selectors use defaults (no dependencies or extra inputs).
Configured selectors never silently default. Each record must have a unique safe
new item ID distinct from all source IDs. The selected source operation's product,
operation version, schema declarations, requested authority and claim ceiling are
unchanged. Source dependencies and original input file references are not copied.
The request template and mapping can explicitly set domain request identifiers;
Flow does not invent these. Map operation-specific request/idempotency identities
where distinct jobs require distinct identities. Review the preview before saving.

## Save, edit and prepare

Preview creates no files or workspace state. The receipt contains each
`work_item_id`, `json_text`, `sha256`, and `artifact_ref`, plus the full ordinary
plan form. The SHA-256 is of the exact UTF-8 `json_text`, including its trailing
newline. Generated inputs use the existing content-addressed path:

`.moonsuite/products/moonflow/plan-inputs/<sha256-hex>/artifact`

Identical requests share the same object even when their work item IDs differ.
Save validates the whole batch and ancillary files first, refuses a conflicting
saved draft, checks existing object bytes, materializes missing objects, and
publishes the draft last. Repeating unchanged input reuses the same objects and
draft. An existing changed object is refused rather than overwritten. A disk or
process failure during save may leave unreferenced content-addressed objects;
retrying the same command can finish publication. This is not a multi-file
transaction or a concurrent-filesystem-adversary guarantee.

The saved draft contains materialized paths, not live links to the template or
export. Later export/template edits do not change it. Use `plan edit` to choose a
revised input or a new draft ID to materialize a different batch. `plan prepare`
then applies the usual file capture, current catalog, health and graph checks;
conformant import and execution are separate steps. No approved runtime state,
attempt, acceptance, or customer/payment outcome is created by preview/save.

Digests identify raw export text and the existing canonical mapping/template
representation. They are reproducible identities, not signatures or proof of
origin. Save the receipt when import provenance matters: it is printed, not
separately persisted. The draft alone does not retain the original export/mapping.

## Scope and limits

This workflow generates JSON from user-supplied data, not model-authored requests,
expressions, a live API connection or a schema inference system. The owning
adapter remains responsible for domain payload validity and effects. Flow does
not resolve embedded domain paths or fetch assets. Declare required extra files
explicitly and use existing preparation behavior for supported reference capture.

Limits: 1..256 records, 1..64 non-overlapping bindings, export/template at most
1,048,576 UTF-16 code units each, parsing depth 64 for exports and detached
templates, generated UTF-8 requests at most 1 MiB each and 8 MiB total. The CLI
uses existing 16 MiB file-read limits; those reads happen before size rejection.
The inherited declared-plan validator also rejects duplicate IDs, missing batch
dependencies, cycles, unsafe artifact references and invalid generic edits.
The normalized internal records still obey the existing 1,048,576-character
records-import bound. Nested selected values retain their full structure.

Pure host API: `declared_plan_from_payloads_v1(source_graph, mapping,
request_template, records_json, draft_id, recorded_at)`. It returns generated
strings and a `DeclaredPlanDraftV1`; hosts own filesystem containment/materialization.
The native CLI rejects symlinked input files and checks materialization directory
components using the existing plan capture helpers.
